# 前后端一体完整迁移计划（Minecraft 式多线程服务端）

## 一、Summary

将现有"后端单线程计算 + 前端纯渲染"的架构，迁移为 **Minecraft 式的"前后端一体"架构**：

- **一个常驻 Java 进程**同时充当 HTTP 静态服务器 + WebSocket 游戏服务器（不依赖 Maven，javac 直接编译，依赖在 `lib/`）
- **浏览器前端**负责大部分游戏逻辑的本地计算（玩家物理/交互/背包即时反馈），服务器只做权威存储、同步广播与少量逻辑，大幅减轻服务器压力
- **服务端多线程**：区块生成、区块同步、天气、广播等分线程并行（利用多核），线程数量可控避免延迟
- **主菜单**：单人模式（连本地存档）/ 多人模式（连远程服务器），多人开服只需改后端配置文件
- **完整迁移** core 版全部功能：45 槽背包（拖拽/分半/堆叠/存档）、Esc 暂停+设置面板、玩家贴图动画、F3 调试、天气
- **预留模组接口**：前后端各保留一套 Mod API 骨架（注册表/事件/钩子），本次只建结构不实现具体模组功能、不测试，为后期扩展留好扩展点

## 三、目标架构

```
┌─────────────────────── 一个 Java 进程（常驻，多线程）──────────────────────┐
│  ServerMain                                                                 │
│  ├─ HttpServer :8080      → 托管前端页面 + /textures 纹理                    │
│  ├─ GameServer (WebSocket :8081)                                            │
│  │   ├─ 网络线程（Java-WebSocket 自带）接收消息                              │
│  │   ├─ 主协调线程 32Hz：应用权威变更、调度广播                              │
│  │   ├─ ChunkGen 线程池（N 核，默认 2~4）：区块噪声生成 → 就绪队列            │
│  │   ├─ ChunkIO 线程（1）：区块存档异步写盘（复用 core ExecutorService）      │
│  │   ├─ Weather 线程（1）：天气状态模拟（低频，无阻塞）                       │
│  │   └─ Broadcast 线程（1）：状态包批量推送所有客户端（不阻塞主线程）          │
│  └─ 世界数据（权威）：区块 map + 玩家档案（位置/背包）+ 配置                   │
└──────────────────────────────────────────────────────────────────────────┘
          ▲ WebSocket (JSON)
┌─────────┴──────────────────────────────────────────────────────────────┐
│  浏览器前端（JS + Canvas）                                                 │
│  ├─ 主菜单页：标题 + 单人游戏 / 多人游戏(输入地址) / 设置 / 退出             │
│  ├─ 本地模拟：玩家物理/跳跃/冲刺/自动跳跃（复用 core 算法移植到 JS）          │
│  ├─ 本地交互：方块选中(DDA)/放置/破坏 → 即时渲染 + 意图上报服务器            │
│  ├─ 背包：45 槽拖拽/分半/堆叠 → 变更整体同步给服务器（存档+广播）            │
│  ├─ 其他玩家渲染 + 天气渲染 + 掉落物动画                                    │
│  └─ Esc 菜单（暂停/继续/设置/退出到主菜单）+ F3 调试                        │
└──────────────────────────────────────────────────────────────────────────┘
```

### 逻辑分布原则（参考 Minecraft，平衡"前端算大部分"与"权威同步"）
- **前端计算**（即时、无延迟）：玩家物理/移动/跳跃/冲刺、方块选中射线、放置/破坏意图、背包操作
- **服务器权威**（存储与同步，不跑逐玩家物理）：区块生成与存档、方块变更应用与广播、玩家位置接收与广播、背包数据存储、天气状态、配置
- **降低压力**：服务器不做逐玩家物理模拟，只做轻量权威确认和广播

## 四、Proposed Changes（按阶段实施）

### 阶段 A：服务端多线程 + 多玩家重构

**A1. 新增配置文件 `server/config.json`**
- 字段：`wsPort`、`httpPort`、`seed`、`worldName`、`maxPlayers`、`chunkThreads`（区块生成线程数）、`weatherEnabled`、`broadcastHz`
- 作用：单人开服用默认值；多人开服改 `maxPlayers`/`wsPort` 后重启即生效
- 文件：[server/config.json](file:///g:/IntelliJ%20IDEA%202025.3.3/IdeaProjects/Game/server/config.json)（新建）

**A2. 区块生成线程池（多核并行 + 线程锁）**
- 新建 `server/world/ChunkGenWorker.java`：持有一组 `ChunkGen` 线程（数量=config.chunkThreads），每个线程从 `LinkedBlockingQueue<ChunkPos>` 取任务，用 **Perlin 噪声**生成区块到就绪队列
- 修改 `ServerInfiniteMap`：`getChunk` 命中未生成时**不阻塞**——向生成队列提交任务并返回（空/占位区块），由主协调线程从就绪队列取回已生成区块 `put` 进 map（`ConcurrentHashMap` 已有，无需加锁）
- 线程锁：队列用 `LinkedBlockingQueue`（内部锁）；`tileChanges` 用 `synchronizedList`（已有）；区块 map 用 `ConcurrentHashMap`（已有）
- 风险控制：生成线程数默认 = `max(2, CPU核数-2)`，上限 4，避免线程过多导致延迟（用户要求）

**A3. 区块 IO 线程（存档异步）**
- 复用 core `InfiniteMap` 已有的单线程 `ExecutorService` 存档机制，无需新建；确认 `saveAndUnloadOutsideRadius` 与主线程的调用时序（只在玩家换区块时触发，避免每 tick 刷屏——顺带修复阶段一发现的刷屏隐患）

**A4. 天气线程**
- 新建 `server/world/WeatherSystem.java`：独立线程，每 N 秒（默认 10s）更新全局天气状态（`clear/rain/thunder` + 强度 0~1），写入 volatile 字段，主协调线程随状态包广播
- 前端渲染云层/雨滴

**A5. 多玩家重构（核心）**
- 改造 `GameWorld` → 拆分职责：
  - `WorldCore`（世界权威）：`ServerInfiniteMap`、天气、方块变更队列（原 GameWorld 的 map/tick 中世界部分）
  - `PlayerProfile`（每连接一个）：玩家位置 `{x,y}`、朝向、动画帧、背包数据（45 槽数组）、出生点
- 改造 `GameServer`：
  - `ClientState` 持有 `PlayerProfile`，`players` map：`WebSocket -> PlayerProfile`
  - 主协调线程 32Hz：接收各客户端上报的玩家位置/背包/方块意图 → 应用权威 → 组装广播包（所有玩家位置、方块变更、天气）→ 交给 Broadcast 线程
  - 断开连接：移除玩家档案、广播玩家离开
- **不再使用 core 的 `Player` 物理**（物理移前端）；core `BlockInteraction` 仅保留 DDA 选中算法移植参考，服务器不做射线校验（信任前端意图，简化压力）——存档/世界仍用 core `InfiniteMap`

**A6. 模组接口骨架（只建结构，不实现功能、不测试）**
- 新建 `server/mod/` 包：`Mod.java`、`ModContext.java`、`ModRegistry.java`、`ModEventBus.java`、`ModEvent.java`、`ModLoader.java`（详见"五之补"节）
- 全部为接口/空实现骨架，不接入主流程，仅保证 javac 编译通过

## 五、Assumptions & Decisions（决策记录）

1. **前后端一体**：浏览器前端 + 常驻 Java 进程（HTTP+WS 同进程），单人=连默认存档，多人=改 `config.json` 后重启开服，客户端程序本身即服务端
2. **逻辑分布**：前端算玩家物理/交互/背包（即时）；服务器权威存储+广播+区块生成，**不跑逐玩家物理**（符合"减轻服务器压力"）
3. **多线程**：区块生成池（2~4）、ChunkIO（1，复用 core）、天气（1）、广播（1）、主协调（1），共 6~8 线程，可控不超载
4. **背包**：前端 45 槽完整实现，整体同步给后端保存与广播（用户已确认）
5. **服务器信任前端意图**：不做射线/物理校验（简化，单机小规模够用）；如需防作弊后续加校验
6. **多玩家**：每连接独立 `PlayerProfile`（位置/背包），世界共享一个
7. **存档**：世界区块用 core `InfiniteMap`（含 ChunkGen 线程池改造后仍兼容），玩家档案（位置+背包）写 `player_<id>.txt`
8. **不引入 Maven**：继续 javac + `lib/` 依赖
9. **设置面板**：前端实现（按键绑定/服务器地址记忆），后端不参与
10. **天气**：仅影响渲染（云/雨），不影响物理；状态由服务器 WeatherSystem 权威下发

## 五之补、模组接口设计（Mod API 骨架，本次不实现功能、不测试）

为后期模组扩展预留稳定扩展点。原则：**只建结构、留扩展点、不实现具体功能、不测试**，接口保持最小且向后兼容（避免后期加东西要返修）。

### 后端 Mod API（Java）
新建 `server/mod/` 包（骨架类，仅接口+空实现，不在主流程中调用）：

| 接口/类 | 用途 | 扩展点 |
|---|---|---|
| `Mod.java`（接口） | 模组主入口：`init(ModContext)` / `id()` | 后期加载 .jar 模组时实现 |
| `ModContext.java` | 给模组的上下文：注册表/事件/配置句柄 | 后期扩展方法 |
| `ModRegistry.java` | 方块/物品/实体注册表（基于 core `Block.REGISTRY` 模式扩展） | `registerBlock(id, name)`、`registerItem(id, name)`、`registerEntity(id)` |
| `ModEventBus.java` | 事件发布/订阅：`subscribe(EventType, handler)`、`post(event)` | 方块破坏/放置、玩家加入/离开、tick、存档前后事件 |
| `ModEvent.java`（抽象基类） | 事件数据载体 | 具体事件类后期加 |
| `ModLoader.java` | 扫描/加载模组（`mods/` 目录） | 本期只做目录扫描占位，不实际加载执行 |

### 前端 Mod API（JS）
在 [game.js](file:///g:/IntelliJ%20IDEA%202025.3.3/IdeaProjects/Game/server/src/main/web/game.js) 顶层挂 `window.GameModAPI` 骨架对象：
- `GameModAPI.registerBlock(id, renderFn)`：自定义方块渲染钩子（后期实现）
- `GameModAPI.registerItem(id, meta)`：自定义物品元数据（图标/堆叠上限）
- `GameModAPI.on(event, handler)`：事件订阅（`blockBreak`/`blockPlace`/`playerJoin`/`playerLeave`/`tick`）
- `GameModAPI.events`：内部事件派发器（空实现，接口可用）

### 兼容性约定
- 注册表 ID 使用字符串命名空间（如 `"minecraft:grass"`），避免数值 ID 冲突，后期加模组不必改既有 ID
- Mod API 方法签名固定，只增不改（新增重载/方法，不修改已有签名），保证后续不返修
- 本阶段模组接口不接入主流程、不测试（用户明确要求），仅保证编译通过
